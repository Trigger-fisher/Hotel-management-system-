## 1. Stack and Next.js 16 rules

| Part | Choice |
|---|---|
| Server | Next.js **16.3.8** (App Router, Turbopack, React 19.2, React Compiler on), TypeScript strict. API = Route Handlers under `web-app/src/app/api/v1`. Node runtime only. |
| Database | PostgreSQL 18, HMS's own instance `127.0.0.1:5433`; driver `pg`. No ORM. |
| Libraries allowed | `pg`, `argon2`, `zod` (4.6.5), `nodemailer`, `pdfkit`, `tsx` (+ types). Anything else needs MJ's OK. No Redis, Docker, separate backend server. |
| Tests | built-in `node:test` through `tsx`. No test library. |
| No mobile app | Web only (MJ, 06 Oct). The word `mobile` in a field is a phone number and stays. |

**Next.js 16 facts the backend relies on** (from `web-app/node_modules/next/dist/docs/01-app`, read before changing anything; the repo's `web-app/AGENTS.md` says this is not the Next.js of older training data):
- A Route Handler is `route.ts` exporting `GET POST PUT PATCH DELETE HEAD OPTIONS`. Unsupported method = 405. `OPTIONS` is automatic if not defined. A `route.ts` cannot sit beside a `page.tsx` at the same segment.
- `context.params` is a **Promise** (`await ctx.params`); typed with the global `RouteContext<'/path/[id]'>` helper (generated by `next dev | build | typegen`).
- `request` is a `NextRequest` (`request.nextUrl.searchParams`, `request.cookies`). `cookies()` and `headers()` from `next/headers` are async; `headers()` is read-only (set headers by returning a `Response`).
- **Handlers are NOT cached by default** (changed in v15). Only `GET` can opt in (`dynamic = 'force-static'`, `revalidate`). HMS never opts in: every response also carries `cache-control: no-store`.
- Segment config used in HMS: `runtime = 'nodejs'` (the DB driver and argon2 need it). Webhooks use `request.text()` (no body parser config). Streaming and `FormData` work through Web APIs.
- `instrumentation.ts` `register()` runs once at server start; HMS starts the mail worker there (`NEXT_RUNTIME === "nodejs"` only).
- `next.config.ts`: `serverExternalPackages: ["pdfkit"]` (pdfkit reads data files at run time), `outputFileTracingIncludes` copies PDF fonts into every `/api/**` build, `reactCompiler: true`, `poweredByHeader: false`, security headers (`Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`), `NEXT_DIST_DIR` lets builds avoid the dev server's `.next`, Turbopack `root` is the repo root because `ui-shared/` sits beside `web-app/`.
- Every file under `src/server` and `src/db` starts with `import "server-only"` so a client import is a build error (tests use `src/server/lib/node-hooks/register.ts` to make it a no-op).
- Middleware is `proxy.ts` in Next 16 (not used by HMS today; the wrapper does auth per route).

## 2. Code layout and the layer rule

```
web-app/src/app/api/v1/<module>/...     route files: wrapper exports only (210 routes)
web-app/src/server/
  http/        route.ts (the door), wrapper.ts (the implementation), respond.ts, trace.ts, idempotency.ts, limits.ts, meta.ts
  auth/        session, permission engine (can), catalog.generated.ts, password, codes
  services/    admin auth billing cash companies frontOffice overview payrollCore payrollPay website  (rules, validation, DTO mappers, zod schemas)
  repos/       interfaces (no SQL)   repos/memory/ in-memory doubles   repos/postgres/ real repositories
  compose/     the ONE place that picks real vs in-memory (by DATABASE_URL + HMS_HASH_KEY), mail worker, recycle
  documents/   pdfkit renderer, layout kit, bundled fonts (Inter, Noto Sans Gujarati/Devanagari)
  money/       integer paise maths, PHP 8.3 round() port        crypto/ keyed hashes only      errors/  logger/  validation/  config/  data/ (entryNo)  db/ (ids, pgErrors)
web-app/src/db/    pool.ts (ONE shared pool), withHotel.ts, schemaName.ts, singleStatement.ts, convert.ts
web-app/src/instrumentation.ts            starts the mail worker
db/migrations/{platform,hotel}  db/seeds/{platform,hotel,source}  db/scripts/ (cli, migrate, create-hotel, pg-instance, pg-setup, lint-sql, generators, php/ golden-fixture generators)
ui-shared/        the contracts both sides share (types, mocks, copy). Owned by the Lead; the backend never edits it, it files a "contract request" (section 7.9)
```

**Layer rule** (ESLint `no-restricted-imports` + `tests/server/layers.test.ts`): `route -> service -> repository interface -> (Postgres | in-memory double)`.
- A route imports only the wrapper, a schema and the composed service; never a repository, `src/db`, or `pg`.
- A service imports interfaces only; never a memory repository, `src/db`, `pg`.
- `pg` appears only under `src/db` (and `src/server/db`). No SQL, engine names, SQLSTATEs or schema/role names outside those folders.
- Route files export only wrapper-built methods; `z.object` is forbidden in routes (use `z.strictObject`).
- `no-console` is an error in `src/server`, `src/db`, `src/app/api`, `db/scripts` (use the logger).

**Real vs in-memory.** `compose/*` uses the PostgreSQL repositories when `DATABASE_URL` and `HMS_HASH_KEY` are set (made by `db:cli setup`); otherwise the in-memory doubles (nobody can sign in, there are no users). The doubles are the reference contract: every concurrency test must pass against both. The double may be stricter than the database, never looser.

## 3. Binding rules (builders)

1. PostgreSQL only. One schema and one role per hotel; `withHotel` is the only door. MySQL files are removed.
2. **Plain data** (MJ): no field encryption, no sealing, no blind index. Passwords, codes and tokens are always HASHED (argon2 / keyed HMAC) and never logged; ID and bank numbers are never logged (redaction test stays).
3. Money is `bigint` paise through `money/` (PHP 8.3 `round()` port, half away from zero, exact decimals). DTO amounts follow `ui-shared`; ids are UUID strings; times are UTC `Date`/ISO. Never float, never PHP 8.4 rounding.
4. Every route goes through the one wrapper (session, permission, same-origin, strict zod, idempotency on money creates, `{data}`/`{error}` envelope, traceId).
5. Every write that changes money or a record carries the optimistic `version` (trigger enforces +1) and writes its audit/log row in the SAME unit; a failing log write rolls the action back (test it).
6. Entry numbers only through `nextEntryNo` (advisory lock, `MAX+1` including soft-deleted rows); UNIQUE is only the backstop.
7. Soft delete by default; hard delete only on tables marked `-- hard-delete:` with a cited reason; the recycle ability stays derived.
8. Search is case-insensitive like Pallav (`lower()`/`ILIKE`/`citext`, never ASCII-only); one lookup method per picker, limit ≤ 50; statements/ledgers capped (5,000 rows, 3 years).
9. Parameters only; never stacked statements or string-built SQL (`hms_app` can `SET ROLE` into any hotel role; only this rule and `singleStatement` stop abuse).
10. Tests come with each unit: golden against real PHP output for Pallav maths, concurrency (`Promise.all`) on the double AND the real DB, isolation (A cannot see B), permission matrix at all four levels, hostile input. Whole-project `tsc` and the server suite green before a *final* report (MJ: do not run them constantly; single files while working).
11. Real-DB tests use `lockTestDatabase()` (shared `hms_test`); never wipe while another run is active.
12. Disk is tight: never leave build folders, Chrome profiles or test hotels behind.
13. New tables/columns: a forward-only migration file with a rollback note; never edit an applied migration (checksum).
14. Secrets: scripts generate them; never print, commit or paste a value; names only in the register (section 10).
15. Identity never comes from input: actor, role, hotel id, `recordedBy`, `isAdmin`, `sentBy` are read from the verified session.
16. Services call only repository interfaces; no engine names above `src/server/db`.

## 4. Database (PostgreSQL 18)

### 4.1 Instance and roles
- HMS's OWN instance, a normal user process (no Windows service): binaries `C:\Program Files\PostgreSQL\18\bin`, data `%LOCALAPPDATA%\HMS\pg\data`, port **5433**, `127.0.0.1` only, `scram-sha-256`, UTC. Controlled by `npm run db:pg -- ensure|status|stop` (`db/scripts/pg-instance.ts` refuses any other data folder). The machine's other PostgreSQL install (port 5432, lost password) and Hotel Pallav's MySQL are **never touched**.
- One database `hms` (and `hms_test` for tests): shared schema `platform` plus one schema and one NOLOGIN role `hotel_<32 hex>_rw` per hotel.
- **A hotel's schema is named for the hotel** (MJ, 2 Nov 2026; platform migration 0172): `<group>_<hotel>` for a hotel of a real group, `<hotel>` for an individual hotel (lower-case letters, digits and single underscores, at most 63 characters; `sunrise_group_hotel_sunrise_rajkot`, `blue_lagoon_residency`). A name with no usable letters becomes `hotel`; a leading digit gets `h_`; a system name, or a name another hotel or schema already has, gets `_` and the last 6 characters of the hotel id. The name is made in ONE place, `platform.hotel_schema_name_for(hotel_id)`; `create-hotel` and `provisionHotel` call it before they build a schema, so every new hotel is created in this format and no other. It is stored in `platform.hotels.schema_name` (no longer generated from the id) and the app reads it through `web-app/src/db/schemaDirectory.ts` (5 s cache). **The role is never renamed**: it stays `hotel_<32 hex>_rw` from the id (`platform.hotels.role_name`), so isolation is exactly as before. `npm run db:cli -- rename-schemas` (dry run) / `-- rename-schemas --apply` brings every existing hotel's schema to its readable name (one hotel per transaction, audited as `hotel.schema_renamed`) and can be run again after a hotel joins a group or is renamed. Take `npm run db:cli -- backup` first. guests, companies, platform admins and the super admin are rows in `platform`, not schemas.

| Role | Purpose |
|---|---|
| `hms_owner` | Owns `platform` and every hotel schema; `CREATEROLE` only (no superuser/createdb/replication/bypassrls); runs migrations, seeds, create-hotel; never serves the app. |
| `hms_app` | The app's login. `NOINHERIT`, no DDL, nothing on any hotel schema; it can only `SET LOCAL ROLE hotel_<hex>_rw` inside a transaction. Per-table rights on `platform` from the grants file. Role limits: `statement_timeout` 15 s, `lock_timeout` 5 s, `idle_in_transaction_session_timeout` 10 s, `timezone` UTC. |
| `hotel_<hex>_rw` | SELECT/INSERT/UPDATE on that schema's tables, DELETE only on `-- hard-delete` tables; nothing anywhere else. |

`REVOKE ALL ON SCHEMA public FROM PUBLIC`; `hms_app` has no access to `public`. Known limit: `hms_app` is a SET member of every hotel role, so isolation against a stacked-statement injection also relies on the app refusing a second statement.

### 4.2 `withHotel` (`src/db/withHotel.ts`)
`BEGIN` → `SET LOCAL ROLE "hotel_<hex>_rw"` → `set_config('search_path','hotel_<hex>, pg_catalog', true)` (never `platform`/`public`) → work → `COMMIT` / `ROLLBACK`. The hotel id comes from the verified session and is validated as a strict UUID **before a connection is taken**; schema/role names are built only from validated UUIDs. One statement per query. A broken connection is destroyed, never returned to the pool; every checked-out client has an `error` listener and a query timeout (default 20 s). ONE shared pool (`DB_POOL_MAX`, default 20). Never hold a transaction open across an `await` on something that is not the database (email, HTTP). Group admins/platform staff reach other hotels only through a separate audited path (`withHotelAs`, audit row first; not built yet).

### 4.3 Conventions
- Ids `uuid DEFAULT uuidv7()` (the app may mint its own with `newId`); times `timestamptz` (UTC; shown in IST by the UI; stay nights = `date`); booleans `boolean`; closed sets `text` + `CHECK`; JSON `jsonb`; money `<name>_paise bigint` with an explicit sign rule; percentages `numeric(5,2)` with a range CHECK.
- Names snake_case, plural tables; FK + index on every FK and every list filter/sort column, added in the same migration.
- Live-row uniqueness = **partial unique indexes** (`WHERE deleted_at IS NULL`, `WHERE revoked_at IS NULL`, `WHERE legacy_id IS NOT NULL`). Case-insensitive rules (username, email, names) use `citext` or a `lower()` index so lookups match Pallav.
- Rules that must hold at every moment are triggers raising `EXCEPTION ... USING ERRCODE` (version +1 step, one in-house stay per room, insert-only audit tables, role-vs-hotel scope guard). A cascade fires no trigger, so FKs on soft-delete and append-only tables are `RESTRICT`.
- Errors are read by **SQLSTATE, never text** (`src/server/db/pgErrors.ts`): 23505 unique, 23503 FK, 23514 check, 23502 not null, 55P03 lock timeout (→ CONFLICT), 40P01 deadlock / 40001 serialization (retry once, pure DB work only), 42501 privilege, 08xxx connection lost.
- The driver returns `bigint`/`numeric`/`date`/`time` as **text** and `timestamptz` as `Date` (`src/db/pool.ts`); repositories convert with `src/db/convert.ts` (exact bigint, `toSafeNumber` fails above 2^53−1, millisecond truncation, `istDay`).
- GST rates, prices and hotel settings are data (dated tables or settings), never constants. Check-out percents: settings `checkout.hotel_gst_percent` / `checkout.food_gst_percent` (default 5), stored on each stay and bill. Bill header GSTINs: `billing.hotel_gstin`, `billing.food_gstin`. SAC (HSN/SAC on a tax invoice): rooms 996311, restaurant food 996331 (MJ 5 Nov 2026; `GST_SAC` in ui-shared billing, HMS-wide, no hotel setting), stored on each bill when it is made (`bill_master_bills.hotel_sac` / `food_sac`, hotel 0061, 4 to 8 digits) and never changed by an edit.

- Group admin and platform admin access is a separate audited path.

### 4.6 Seeds, runner, create-hotel
- **Seeds** (`db/seeds`): idempotent, first line `-- seed: ...`, only `INSERT ... ON CONFLICT`, no secrets, tracked in `schema_seeds`, immutable once applied. Platform seeds are GENERATED by `generate-platform-seeds.ts` from `db/seeds/source/pallav-permissions.json` (13 modules, 37 parts, 6 abilities) and role grants (viewer, editor, admin, super_admin, guest, corporate); a role's level is the highest of view<create<edit<full it holds. Hotel seeds (`0001_defaults`): two business units, ten master lists, eight expense heads per business, five ID proof types, four shared payroll lists, the two fixed payroll companies named after the hotel, check-out GST settings, the two single website rows. `npm run seeds:check` fails on drift.
- **Runner** (`db/scripts/migrate.ts`, as `hms_owner`): platform first, then every hotel schema; one transaction per file per schema with version + checksum recorded inside it; changed checksum stops the run before anything is applied (all hotels checked first); global session advisory lock; failures name only schema, file and SQLSTATE; `-- migrate: no-transaction` for `CREATE INDEX CONCURRENTLY`; safe on live data (nullable → backfill → NOT NULL). `cli migrate` also re-syncs DELETE grants from the markers.
- **create-hotel**: ONE transaction (platform row, schema, role, grants, migrations, seeds, audit); a failure leaves nothing behind.
- **Entry numbers** (`src/server/data/entryNo.ts`): `pg_advisory_xact_lock(hashtextextended(current_schema()||'.'||table,0))` then `MAX(entry_no)+1` over all rows including soft-deleted (gaps stay; deleting the last frees its number); lock timeout → CONFLICT; table from a fixed list of 13 books, never request input. Stay/bill numbers and `site_reference_counters` (reset each fiscal year 1 Apr–31 Mar IST, `ON CONFLICT DO UPDATE ... RETURNING`) follow Pallav.

### 4.7 Migration/SQL lint (`db/scripts/lint-sql.ts`, `npm run lint:sql`, also in `npm test`)
1. First line `-- rollback: <statements>` or `-- rollback: forward-only because <reason>`; `NNNN_snake_name.sql`, unique ascending.
2. Platform tables are `platform.<name>`; hotel tables unqualified; a hotel file has no `GRANT/REVOKE/ALTER DEFAULT PRIVILEGES` (privileges belong to create-hotel); platform tables appear in a GRANT or carry `-- no-app-access`; a platform table in a file ≥ 0100 is granted in that same file.
3. Every table: `id uuid PRIMARY KEY`, `created_at/updated_at timestamptz NOT NULL` + `touch_updated_at` trigger (or `-- append-only` with an `at` column, or `-- no-standard-columns: <reason>`).
4. Every FK column is the first column of a PK/UNIQUE/full index.
5. No float/double/real/money/serial/`timestamp` without zone; money columns `_paise bigint`; a money-looking name must be `_paise`.
6. Text columns named status/kind/level/purpose/outcome/event/client carry a CHECK. `DROP` uses `IF EXISTS`. Append-only tables have no `SET NULL/CASCADE/SET DEFAULT` FK.
7. Hotel: nullable `legacy_id` + partial UNIQUE, soft-delete columns, `-- hard-delete:` markers (with citation; every recycle-bin table has one), version trigger for `version` columns.
8. No encryption-shaped columns. Seeds: header, `INSERT ... ON CONFLICT` only, no DDL/UPDATE/DELETE/TRUNCATE/GRANT, no password hash, key or token.

## 5. Security

### 5.1 What is stored how
| What | Stored as |
|---|---|
| Password | Argon2id (OWASP min 19 MiB / 2 passes / 1 lane; rehash on login when parameters change). Rule: 8–128 chars with upper, lower, number, special (Pallav's regex over bytes, golden-tested against PCRE). Unknown username costs the same dummy verify. |
| Refresh/reset-link/invite tokens, session token | 256 random bits; plain SHA-256 (64 hex) |
| 6-digit emailed code | keyed HMAC-SHA256 under `HMS_HASH_KEY`, bound to purpose + user + code (`hashAuthCode`); a bare hash would fall to 10^6 tries |
| Username/mobile/email in sign-in records, rate-limit keys | keyed HMAC (`hashIdentifier`) |
| Challenge / change tokens | signed statelessly under `HMS_HASH_KEY`, bound to the device or password hash |
| ID/bank/emergency numbers, outbox address | plain columns (MJ, final). Risk note below. |
| Integration secrets (Google, SMTP, Razorpay, backup) | stored as typed (settings) or env; **never returned by any API** (`set: true\|false` only) |

Compare hashes with `safeEqualHex` (constant time); hashed messages are length-prefixed under a domain label. **Risk note (MJ accepted):** plain bank/Aadhaar/PAN/ID numbers are readable by anyone with database, backup or disk access (DPDP Act exposure). Safeguards that keep the decision: encrypt server disk and backup storage at OS/hosting level and keep backups private; never log such values; app role has no DDL or cross-hotel access; show these only to roles with permission and keep them out of lists/PDFs unless needed; protect and rotate DB passwords.

### 5.2 Hotel isolation
Per section 4.1/4.2. A wrong schema name gets *permission denied* (42501) from PostgreSQL itself. Hotel from the verified session only. A foreign hotel's record id is 404, never 403. Proven by `tests/db/isolation.test.ts` and per-module isolation tests. Platform tables are reached only through the platform data layer.

**Row-level security for the portals (T8, 13 Oct 2026, hotel migration 0035):** the second fence under the service code. `withHotel` sets, per transaction and only when the session carries a record scope (a guest or company account; `repos/postgres/unit.ts` passes `session.scope`), `hms.scope_kind` (`guest` | `company`) and `hms.scope_id` with `set_config(..., true)` right after the search path (`SET_SCOPE_SQL`; a scope that is not a UUID is refused before a connection is used). Policies on `customers`, `company_profiles`, `bill_master_bills`, `bill_master_advances`, `pms_stays`, `pms_reservations`, `pms_charges` and `guest_requests` pass every row when no scope is set (staff, visits, the workers, the nightly copy) and otherwise allow a guest their own customer row, the bills, advances and stays with no company whose mobile's last 10 digits are their customer's (the `mobileForms` rule), the stays of their bills, the reservations and advances of those stays, and the charges and requests of those stays; a company its profile and its company rows plus the stays of its bills. A policy that subselects another protected table is filtered by that table's policy, so the fence holds from any direction. Proven on the fake pool (`tests/server/withHotel.test.ts`: the statement, its place, staff send none) and written for the real database in `tests/db/portalRls.test.ts` (two guests, two companies, staff; plain SELECTs, an UPDATE on another guest's row touches nothing, an INSERT for another guest's stay is 42501); **that real-database run has not happened in this environment** (no PostgreSQL here): run `npm run test:db` on the dev database before the Neon SQL, and open both portals once after it.

### 5.3 Permission engine (`src/server/auth`)
`VerifiedSession` (user, hotel, account role, `roleKey`, `roleLevel`, effective permissions, session, client, and for guest/corporate the company/guest they are limited to) and `can(session, catalog, key, level)` over Pallav's 13 modules / 37 parts / 6 abilities (`catalog.generated.ts`, generated from the same source as the seed). Follows Pallav's `Access::effective()`: role grants (own + inherited) → the person's grants/revokes for THIS hotel → each module spread over its parts (a part revoked by name stays revoked). Effective level on a part = `min(granted, highest level the part offers)`. Guest/corporate have no module rows (`can` false everywhere); they see only their own records (`recordScopeOf`). No super-admin bypass. Server-side check on every endpoint; a missing permission = 403 and an audit row for write attempts. A hotel admin may change roles/grants/attachments only for their own hotel and never a built-in role or platform admin (service rule + audit). `platform.user_permissions` is per hotel; triggers guarantee a custom role belongs to a hotel the person is attached to.

### 5.4 Sign-in (rules in `docs/specs/login.md`)
- Username **or email** + password, then an emailed 6-digit code when required (**always for admin roles**). No authenticator app, recovery codes or Google sign-in. Temporary/admin-reset password forces a change.
- Five wrong passwords lock for 15 min → 30 min → 1 h → 3 h → 8 h → 24 h; a stranger's failures never end the owner's session; only an admin block (no timer) ends sessions and a reset does not lift it. Messages and timing never reveal whether an account exists (forgot-password always answers the same; dummy challenge; mail through the outbox).
- Codes: valid 10 min, five wrong cancels the code, ten wrong reset codes per 24 h stops new ones for 24 h, resend every 30 s and five per hour. Counters live in `platform.rate_limits` (survive restart; committed even when the request is refused via `failAfterCommit`).
- Cookie `__Host-hms_session` (`Path=/; HttpOnly; Secure; SameSite=Lax`, no Domain), 256-bit token, SHA-256 stored; same-origin check on cookie writes and public writes; abilities in the user come from the permission snapshot of the hotel the session was opened in. A platform owner with no hotel has `hotelId = ""`: auth routes only, no hotel schema.
- The person is emailed on password change, lock and new sign-in.

### 5.5 Logging and the rest
- The logger writes one JSON line per call; everything passes `redact()` (keys: password, token, authorization, cookie, reset/login code, Aadhaar, ID proof, account number, IFSC, card, CVV, signature; text scrubbed for Bearer tokens, JWTs, 12-digit Aadhaar, 13–19 digit cards, passwords in URLs, `token=` pairs; depth/array/string caps). Bodies are never logged. Config/crypto errors name the variable, never the value.
- SQL injection: values only via `$n`; the only built string is the validated schema/role name and allow-listed table/column names; hostile-input tests on every search/sort parameter.
- Audit: hotel actions go to Pallav's `system_logs` (+ `trace_id`) in the same unit as the change; platform audit in `platform.audit_log` (insert-only). Force-mode actions also go to `force_logs`.
- Hard-delete rules and the stay-charge exception (`pms_charges` is hard-delete but money: refuse after check-out/billing and log the deleted line in the same transaction).
- Razorpay (when built): verify the webhook signature BEFORE dedupe, paise integers, no refund double count. Media: ID proofs never on a public disk, every download checks permission.
- DPDP: purpose-limited fields, anonymisation path designed (not built), consent flags for portal users.

## 6. API: wrapper, envelope, errors

Base `/api/v1`, JSON only. Success `{ "data": T }` (room beside `data` for meta); error `{ "error": { "code", "message", "traceId", "details?" } }`; never both. Every response has `x-trace-id` and `cache-control: no-store`. Money = integer paise; dates ISO strings (`YYYY-MM-DD`; moments ISO UTC). A GET never writes a row; the one exception is the `/cron/*` entry points (Vercel Cron calls GET), guarded by `CRON_SECRET` (7.7).

### 6.1 The route wrapper (`src/server/http/route.ts` → `wrapper.ts`)
A route file exports only methods built by `route()` or `publicRoute()`:
```ts
export const POST = route({
  permission: "session",            // or { key: "revenue", level: "view" }
  body: depositCreateBody,          // z.strictObject: unknown keys refused, strings/numbers bounded
  idempotency: "optional",          // "required" for money that must not be created twice
  limits: [],                       // only where Pallav throttles: { name, max, windowSeconds, by: "user"|"session"|"ip" }; all counted at once (18 Oct 2026), so a request the first limit refuses still counts on the others
  handler: async ({ session, body, request, traceId }) => ({ data: await getCashRevenue().create(session, body, requestMeta(request, traceId)), status: 201 }),
});
```
Order of checks, the same everywhere:
1. **Trace id**: reuse a good incoming `x-trace-id` (8–64 of `A-Za-z0-9_-`), else new.
2. **Session** (signed-in routes): none/invalid → `401 SESSION_EXPIRED`. Hotel from the session only.
3. **Permission** `{key, level}` or `"session"`; else `403 FORBIDDEN`. Input is never examined for someone who failed 1–2.
4. **Same-origin** for cookie sessions on writes (`Origin` = host or `Sec-Fetch-Site: same-origin`), else 403.
5. **Strict, bounded input** → `422 VALIDATION_FAILED` with field names only (values never echoed): path params, query (repeated name refused), JSON body (content type, 256 KB cap, `z.strictObject`). Lists use `listQuerySchema(sorts, default)`: `sort` whitelist, `pageSize` ≤ 100 (UI sizes 10/25/50/100), `search` ≤ 100 chars without control characters.
6. **Throttles** (`limits`): counted before the handler; over → `429 RATE_LIMITED` + `Retry-After`; store `platform.rate_limits` (in-memory in tests; with a database it is the table, so a dev-server restart does NOT clear it: `npm run db:cli -- clear-rate-limits` does). DEV ONLY: with `NODE_ENV=development` AND `HMS_DEV_RELAX_LIMITS=1` (only in the git-ignored `web-app/.env.local`, never in `.env.example` or a deploy config) the sign-in throttles `login` and `login-ip` allow 200 instead of their max, for this PC only (`http/limits.ts effectiveMax`; production, test and any other value ignore it, tested in `limits.dev.test.ts`). No throttle where Pallav has none.
7. **Idempotency-Key** on writes (8–128 of `A-Za-z0-9_-`; belongs to person + hotel; stored 24 h): same key + same request replays (`idempotent-replayed: true`); other body/endpoint → `422 IDEMPOTENCY_KEY_REUSED`; still running → `409 REQUEST_IN_PROGRESS`; a failed request releases the key. The hash covers method + path ids + query + body.
8. **Handler** returns `{data, status?}`. Updates and deletes carry the record's `version`; stale → `409 CONFLICT` with `details.currentVersion`.
9. **After a failure**: `failAfterCommit(fn)` work (wrong-code counter, lock) still runs; its own failure is only logged.
PDFs use a `binary` result type (bytes + headers) with the same trace header. Writing to a PART (e.g. `revenue.hotel`) is checked by the SERVICE (`requirePermission(session, catalog, "revenue.<book>", level)`) because the route cannot know the book before parsing. Levels: create = `create`, edit = `edit`, delete = `full`.

**ETags on list reads (T2, 13 Oct 2026):** a signed-in GET route that sets `cache: "private, no-cache"` (103 of them on 5 Nov 2026, grep `cache: "private` under `app/api/v1`: the hotel staff's and the platform's list and report reads, the dashboard, the bell, the front-office board and the conversations lists and summary; the guest and company portals, My Profile, My mailbox, Pathik, search and settings stay `no-store` so personal data never sits in a browser's disk cache) answers with a weak `ETag` over the `{data}` body (`jsonOkRevalidated`, SHA-256, 27 characters) and, when the request's `If-None-Match` names it (or `*`), a `304` with no body and the same headers. `private, no-cache` means the browser keeps the last answer but asks every time, so a list is never stale; what is saved is the bytes on the wire and the repaint of an unchanged page. The server still builds the data (a 304 is as cheap as the query, not cheaper); every other answer, and every error, stays `cache-control: no-store`. Test: `tests/server/wrapper.test.ts` ("a list read with `cache` ...").

### 6.2 Errors (`src/server/errors/codes.ts`)
Codes come from the `ui-shared` unions (`AuthErrorCode`, `DashErrorCode`); adding one there fails the type check until it gets a status here. Apps show their own text per code; `message` is short safe English (Pallav's wording where the spec says so), never SQL, stack, password, token or ID.

| Status | Codes |
|---|---|
| 400 | RESET_LINK_INVALID |
| 401 | INVALID_CREDENTIALS, INVALID_CODE, SESSION_EXPIRED, SESSION_REPLACED, SESSION_REVOKED |
| 403 | FORBIDDEN, ACCOUNT_DISABLED, ACCOUNT_BLOCKED, PASSWORD_CHANGE_REQUIRED |
| 404 | NOT_FOUND (also another hotel's id) |
| 409 | CONFLICT (`details.currentVersion`), REQUEST_IN_PROGRESS |
| 410 | CHALLENGE_EXPIRED, RESET_LINK_EXPIRED |
| 422 | VALIDATION_FAILED, PASSWORD_TOO_WEAK, PASSWORD_REUSED, IDEMPOTENCY_KEY_REUSED |

`details`: `fields` (name → problem, never the value), `retryAfterSeconds` (also `Retry-After`), `attemptsLeft`, `currentVersion`. Error rule per module: 422 + `details.fields` for form rules, 403 for role refusals, 409 for state, 404 missing, and the sentence is always in `error.message`.

## 8. How to build a new module (copy `Daily Cash, Revenue`)

1. **Spec first**: `docs/specs/<module>.md`: every rule, every validation message word for word, permission key and level per action, number formats, entry-number and recycle-bin behaviour, each cited to Pallav file:line; mark deliberate HMS differences.
2. **Golden tests next**: wherever Pallav has a function (words, search, stamps, totals, IST boundaries, tax, rounding) a PHP generator (`db/scripts/php/generate-<module>-fixtures.php`) runs the REAL function and writes `fixtures/*.json`; the TypeScript is then written to match.
3. **Repository interface** (`repos/<module>.ts`): plain records, table rules in comments, bigint paise, no SQL; the in-memory double (`repos/memory/<module>.ts`) honours entry numbers, soft delete, version, CHECKs, one unit at a time per hotel, rollback on throw, per-hotel data; then the Postgres repo (`repos/postgres/<module>.ts`) passes the SAME tests.
4. **Service** (`services/<module>/`): rules, unit of work, system-log line, DTO mapper; pure helpers (`rules.ts`, `validate.ts`, `search.ts`, `stamp.ts`) so each rule is unit- and golden-testable. In order: re-check the part permission → load inside one `unit.run(session, …)` → apply people-rules and locks BEFORE writing → check version (`CONFLICT` + `currentVersion`; the repo also updates `WHERE version=$2`) → validate with Pallav's messages → write → write the log line in the same unit → return the DTO (integer paise, ISO dates, derived fields, nothing the contract does not name).
5. **Routes** (`app/api/v1/<module>/…`): wrapper exports only. Compose in `compose/<module>.ts` (the only place that picks real repos).
6. **Tests** through the real route files, then the real-DB twin; then this document (section 7) and `docs/specs`.
7. **Tick the checklist** (section 11).

## 14. Platform and Super Admin API (`/api/v1/platform`, plus the public `/api/v1/onboarding`)

Contract: `ui-shared/dashboards/platform.ts` (`PlatformApi`; types, error words and sample data). Scope: the Platform Admin and Super Admin consoles only (account roles `platform_admin`, `super_admin`). **A Group Hotel Admin (`group_admin`) gets 403 on every route below until the Group console server is built; guest, corporate and hotel staff get 403.** Build state: **built (P2 to P5, 11 Oct): all of 14.1 (createHotel was dropped), 14.2, 14.3, 14.4, 14.5, 14.6, 14.7.** P6 (the one review, hardening, final checks) is next. This table is the agreed contract so both Frontends can wire now. Database: `db/migrations/platform/0102..0108` (hotel lifecycle, groups, invitations, onboarding, enter-hotel visits, audit, settings).

**Rules for every route.** Same wrapper as section 6 (session cookie, same-origin on writes, strict zod, `{data}` / `{error}`); the person is `permission: "session"` plus a service check of the account role. Ids are strings; dates are ISO UTC strings (`YYYY-MM-DD` for `from`/`to`, which are IST dates, inclusive); lists use `page` (1-based) and `pageSize` (10, 25, 50, 100; default 25) and answer `Page<T> = {items, total, page, pageSize}` plus the extra keys named below. A bad query value is 422. Creates accept an optional `Idempotency-Key`. There is no `version` on platform records (the contract has none); concurrent status changes are guarded by a row lock and the state machine (a second suspend is 409). **Every state change writes `platform.hotel_status_history` / `group_history` and an audit row in the same transaction; a failing audit write rolls the change back.** A refused attempt (403/409 on a protected action) is also audited with `result: failed`. These routes never open a hotel schema (except Enter hotel, P4).

**Errors** (code → HTTP, as section 6.2): `VALIDATION_FAILED` 422 with `details.fields` (keys listed per route; the sentence is Pallav-style from `platformCopy.errors`) · `CONFLICT` 409 (`error.message` is the plain sentence the screen shows; state problems such as "already suspended", "not archived", "grace period not over") · `FORBIDDEN` 403 (wrong account role; message "Only the Super Admin can do this." for Super-only routes) · `NOT_FOUND` 404 (also a hotel/user that does not exist) · `RATE_LIMITED` 429 · `SERVER_ERROR` 500 with a traceId. Clients key on `error.code`, never on the number.

**Who:** PA = Platform Admin and Super Admin; SA = Super Admin only.

### 14.7 Enter hotel: the read-only guard (P4)
`enterHotel` creates a `hotel_visits` row (reason, 60 minutes, `read_only` always true) bound to the platform user's session. While it is active, the platform user's hotel routes resolve to that hotel **only for reads**; the server refuses every non-GET/HEAD request of a hotel route family with `403 FORBIDDEN` ("You are viewing {hotel} as platform staff. This is read-only.") and writes a failed audit row; this is enforced in the route wrapper, not by the screens. Every action inside is stamped with the platform user and the hotel (`inside_hotel` true, `visit_id`). Exit, expiry (60 minutes) or a new sign-in ends the visit (audited `hotel_exited`). Guest/ID numbers and bank details are masked during a visit when the masking rule is built (open item). A Group Hotel Admin's access to member hotels follows later.

**As built (P4).** `POST /platform/hotels/{id}/enter {reason}` (reason 5 to 500 characters; 422 on `reason` otherwise; 409 for a hotel that is not active or suspended; 404 unknown) starts a visit in `platform.hotel_visits`, bound to the platform session, valid 60 minutes (`ENTER_HOTEL_MINUTES`), and answers `{ok, hotel {id,name,slug,status}, auditId, visitId, expiresAt, readOnly: true}`. `POST /platform/hotels/{id}/exit` ends it (idempotent; `auditId` only when something ended). Entering again, or another hotel, closes the earlier visit first (with its "left" row); a visit past its 60 minutes simply stops counting and is closed by the next one. **How the guard works:** `createSessionResolver` checks for an active visit of the session (platform_admin / super_admin only) and, if there is one, returns the session as THAT hotel's: `hotelId` = the visited hotel, the hotel's built-in `super_admin` permission role (`access.loadVisit`), no personal grants, `session.visit` set. The route wrapper then refuses every non-GET/HEAD/OPTIONS request to any route outside `/api/v1/platform/`, `/api/v1/auth/` and `/api/v1/profile/` with `403 FORBIDDEN` "You are viewing {hotel} as platform staff. This is read-only." and writes a failed audit row (`hotel_write_refused`, with the visit id and `METHOD /path`) through `onVisitWriteRefused`. This holds for any client, not just the screens. An ended or expired visit, a revoked session, or a hotel that is no longer active/suspended returns the person to the console at the next request. **The app's start-up calls inside a visit.** `GET /auth/session` answers the platform person's own account (`user.role` stays `platform_admin` / `super_admin`) with the visited hotel as `user.hotel`, the hotel SuperAdmin `abilities`, and a `visit {id, hotelId, hotelName, expiresAt, readOnly: true}` block (the banner reads the server's expiry); `GET /profile` works for platform staff (their own account, `hotelName` of the visit is not used) and `GET /profile/preferences` is by person. **Decisions (PM, 2026-10-11):** (1) reads inside a hotel are not audited one by one (volume); the start, the end and every refused write are, all stamped with the visit (`inside_hotel` true). (2) Visit shows the hotel SuperAdmin view; masking of ID and bank numbers during a visit goes on the LATER list (MJ to be told in the P6 summary). (3) DONE (P6): a session with a visit gets `BEGIN READ ONLY` for every hotel transaction (`db/withHotel.ts` option `readOnly`, set by `repos/postgres/unit.ts` when `session.visit` is present), so PostgreSQL itself refuses a write (SQLSTATE 25006) even if the route guard were bypassed; a hotel GET that writes anything would now fail inside a visit (tested on the real database). **Contract requests:** `PlatformActivityAction` needs `hotel_write_refused` and `audit_exported` (with labels); `PlatformEnterResult` gains `visitId`, `expiresAt`, `readOnly`.

### 14.8 Provisioner (create-hotel for the web)
Approving a hotel (and deleting one) needs an owner database login that the running app does not have. `src/server/provisioner/port.ts` defines `HotelProvisioner` (`provision`, `dropHotel`, `exportHotel`). The local adapter reads `PG_OWNER_URL` from `db/.env.local` **only when `NODE_ENV` is not production** (fail closed otherwise with a clear "not configured" error; tested); a production worker is a later job. The URL is never logged or returned.

**As built (P3).** `src/server/provisioner/` holds the port (`port.ts`, `HotelProvisioner.provision({hotelId})`), the local adapter (`local.ts`: reads `PG_OWNER_URL` from `db/.env.local`, NODE_ENV not production, otherwise `ProvisionError("NOT_CONFIGURED")`, never falling back to the app login) and an in-memory fake for tests. It runs `provisionHotel` in `db/scripts/create-hotel.ts`, which shares `buildHotelSchema` with `createHotel`: the pending row is locked `FOR UPDATE`, the schema, role, grants, migrations and seeds are built, and the row becomes `active` with `provisioned_at` in the same owner transaction (the two CHECKs of 0102 need both). A second approve finds the hotel not pending (`NOT_PENDING` → 409); a failed build leaves no schema, no role and the row still pending (tested on the real database). Approval is two steps: (A) check in a console unit, build through the provisioner, (B) in one console unit: activate the pending account, record the decision, write history + audit, mail. If B fails after the build, the hotel is already active but undecided and the next approve completes step B without building again. `db:cli migrate` and `seed` walk only hotels that have a schema (`db/scripts/hotel-schemas.ts`).

### 14.9 Sign-in refusals for platform-managed accounts
Sign-in is refused, after a correct password only, with `ACCOUNT_BLOCKED` (403) and `details.reason`: `hotel_pending` (hotel or its first account waits for approval), `group_pending`, `hotel_suspended`, `hotel_archived`, `hotel_rejected`, `disabled`. Messages never reveal whether an account exists to a stranger. Platform staff (no hotel) are unaffected. `platform_admin`, `super_admin` and group admins sign in with the password alone unless they switched the emailed code on (decision 46).

## 16. Forgot password by an emailed link (platform migration 0113)

Replaces the emailed 6-digit code of "forgot password" (sign-in codes after the password are unchanged).
- `POST /api/v1/auth/password/forgot` `{username}` (a username or an email). ALWAYS 200 with the same body `{sent: true, message: "If an account matches, we have sent a link to its email.", challengeId, sentTo, resendAfterSeconds}` (the last three are placeholders for older screens), whether or not the account exists or is usable, and whether or not a limit was reached. Limits: 10 per minute and 10 per 15 minutes per address; at most 5 links per account in 15 minutes (over it nothing is sent, the answer is the same).
- The mail (kind `reset_link`) carries the address in `HMS_PUBLIC_URL` followed by `/?reset=<token>`. The token is 32 random bytes in base64url (43 characters), valid 15 minutes, single use (a refused password, "Choose a password different from your old one", leaves it usable but counts: the 5th refusal uses it up; only a successful change uses it up otherwise); only its keyed hash (HMAC under `HMS_HASH_KEY`) is stored, in `platform.auth_codes` with purpose `reset_link`; a new request ends the older link; the payload with the link is wiped once the mail is sent.
- `GET /api/v1/auth/password/reset-link/check?token=...` gives 200 `{valid: true}`; an expired, used, unknown or malformed token, or an account no longer usable, gives 404 NOT_FOUND, always the same body. 30 per minute per address.
- `POST /api/v1/auth/password/reset-link` `{token, newPassword}` gives 200 `{done: true}`. The password rules and the strength check come first (422 PASSWORD_TOO_WEAK or PASSWORD_REUSED with `fields.newPassword`, the same for everyone); then the link is taken under a row lock (two clicks cannot both use it) and used up; the password is set, the failed-attempt count and timed lock cleared (an administrator's block stays), every session of the account ended, the person mailed "your password changed", an `auth_events` row `password_reset_done` and an `audit_log` row `password.reset_by_link`. A link no longer good gives 404 NOT_FOUND. 10 per minute and 20 per 15 minutes per address.
- No token and no password in any log, event or audit row (tests: `auth.login.test.ts`, "forgot password by an emailed link" and "step two"). The old code routes (`/auth/password/reset`, `/auth/password/forgot/resend`) are removed from the server.

## 17. Page search on every list route (decision 51, 12 Oct 2026)

## 35. New-mail ping: live mail pages without a held-open server connection (3 Nov 2026; no migration)

- **What it is:** when mail lands for a hotel, a platform desk or one staff login, the server sends ONE tiny message with no content to a Supabase Realtime channel (`web-app/src/server/mail/signal.ts`, sent by `compose/convLive.ts` for every saved change, section 36). The open dashboard listens on its channels with one socket (`web-app/src/lib/mailSignal.ts`, started from `RoleDashboard`) and then asks the normal, checked routes for what is new. The ping carries no subject, name, address or count.
- **Channels:** `m` plus 24 characters of an HMAC-SHA256 (key `HMS_HASH_KEY`) of the kind and the id (`hotel`/`platform`/`person`/`group`), so a name cannot be worked out. `GET /api/v1/mail-signal` (session only, browser staff only: a guest, a company login and an API key get 403) lists the channels the caller may hear: their own mailbox; their hotel (hotel staff, never a visitor); the platform desks (platform staff); their group's inbox (its Group Admin, never during a visit).
- **Settings (Vercel):** `MAIL_SIGNAL_URL` (`https://<project>.supabase.co`) and `MAIL_SIGNAL_KEY` (the project's public anon / publishable key, meant for browsers). Without them the ping is off and everything works as before. The content policy (`web-app/security-headers.ts`) then allows the browser to open that one address (`https:` and `wss:`).
- **Safety net:** the pages keep their timed checks (list 20 s, open thread 10 s, badge 30 s, only while the tab is in front). The ping only makes them ask sooner. A failed or slow ping never fails a delivery (1.5 s cap, errors swallowed).
- **Cost:** the socket is open only while the tab is in front (a hidden tab lets go after a minute and reconnects, asking once, when it is shown again).
- **Tests:** `tests/server/mail.signal.test.ts` (channel names, who hears what, the request sent, the policy address, the socket with a fake socket and timers).
