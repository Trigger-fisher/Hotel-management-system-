## How to write a screen (already proven on 40 screens: read these as examples)
- Read `docs/UI.md` first, then the examples `src/dashboards/groups/payrollCore/Staff.tsx`, `StaffForm.tsx`, `payrollPay/Payments.tsx`, `companies/ProfilesScreen.tsx`, `companies/CustomerForm.tsx`.
- One Blade view = one TSX file; keep every Pallav class name and the element order. Class `className`, `htmlFor`, style objects. Icons: `<Bi name="x" />` (bootstrap-icons name without `bi-`).
- Helpers (import, do not copy): `@/dashboards/pallav/ui` -> Bi, Modal (size sm|md|lg|xl, className "pay-form-modal", staticBackdrop, footer), Dialog (confirm), Dropdown, SegTabs, FilterBar + DateRangeField, FilterMenu, PhoneField, useTableView + Th + Pager + SearchField + EmptyState (list sort/search/paging like pms.js), forms.tsx (FormSection, Field, WizardSteps, WizardNav). `groups/payrollCore/pms.tsx`: Fld (`col-md-N` label + control + error), useWizard + WizardSteps, PayLayout/PayKpi (page head + KPI row), MonthNav, EmptyRow. `groups/companies/pageParts.tsx`: `Page` (Pallav `.page-head` + `.kpi-grid`) for screens outside Payroll.
- The page TITLE and icon come from the menu (`ui-shared/dashboards/nav.ts` pageTitle); never print an `<h1>`. Screens return a fragment.
- Keep our mocks, hooks (`useAsync`, `useSubmit`, `useDebounced`, `useToast`) and validation from `@shared/dashboards/*`. Mock data is the basis; Pallav demo data is in `docs/sessions/S08-fixtures` (JSON). If a field/behaviour exists in Pallav but not the mock: add an OPTIONAL field to the mock file and mention it in your report; if it is a contract change in a file you do not own, ask the Lead (hms-c6) in one line.
- Behaviour Bootstrap/pms JS does is rewritten in React (modals, dropdowns, tabs, collapses, wizard steps, drag, live search). No Bootstrap JS is loaded. `reveal` classes are handled by the shell.
- Do NOT use the old kit (`@/components/ui` Card/DataTable/Button/Modal...) for markup; `@/components/ui` hooks/helpers (useAsync, useSubmit, useToast, errorText, AsyncView) are fine.
- Uploads are UI-only file pickers that remember the file name. PDFs: `PDF_ROUTES` in `ui-shared/dashboards/common.ts`.
- Delete the old unused files of a screen when you replace it. No commits or pushes. Never edit shared files you do not own (kit in `components/ui`, `tokens.ts`, `nav.ts`, icons, `public/pallav`, `pallav/*.ts`): ask. Additive new files in `src/dashboards/pallav/ui/` are allowed (add to ui/index.ts).

## Part 2: wire a group to the real /api/v1 (added 2026-10-06)
Web UI 1 built the real HTTP client: `web-app/src/lib/api/client.ts` (`get/post/patch/put/del` return the dashboards' `DashResult`, envelope `{data}` / `{error}`, cookie session, Idempotency-Key on writes, error mapping; `dash`, `dashMap` helpers) and `mode.ts` (`chooseApi(real, mock)` picks once at load: NEXT_PUBLIC_API=real|mock, `?api=` per page; /dev previews are always mock). Example adapter: `web-app/src/lib/api/adapters/preferences.ts`, and the way `groups/<group>/api.ts` creates its singleton (today `createXApi(...)` from ui-shared/dashboards/x.ts).
Task: for your modules write ONE adapter per ui-shared API (`web-app/src/lib/api/adapters/<module>.ts`) that implements the SAME TypeScript interface (the return type of `createXApi`, e.g. `PayrollCoreApi`; some contracts export an interface, otherwise use `ReturnType<typeof createXApi>`) by calling the real routes, and switch the group's `api.ts` to `chooseApi(() => createXRealApi(), () => createXApi(...mock))`. The truth for routes and shapes is `docs/api/<module>.md` (and `docs/API.md`); the server routes live under `web-app/src/app/api/v1` (look there to see what exists and its exact request/response shapes; read the route files and their zod schemas). Map server shapes to the mock's types in the adapter (the screens must not change). Where the server has no route or a different shape than the mock needs, do NOT invent: implement what exists, return `{ ok: false, error: { code: 'NOT_FOUND', message: 'No route yet' } }`-style via a small helper `notYet(name)` for the rest, and list every gap precisely in your report (method, expected route, what the mock needs). Keep Mobile compiling: do not change ui-shared signatures. The /dev preview must keep using mocks. eslint on the adapter files, one tsc at the end in the background (RAM is tight: never run tsc/eslint in parallel with another agent's build). Final report: adapters written, routes wired, gaps list (the Lead wants it verbatim).
