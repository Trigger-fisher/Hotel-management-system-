# Security notes

## Sign-in: the emailed code is optional (decision 46, MJ, 12 Oct 2026)

**The plain risk: a stolen password is enough to sign in on an account that has the emailed code switched off.**

- The emailed 6-digit sign-in code is no longer compulsory for anyone, administrators included. New accounts start with it **off**; the migration `platform/0114_signin_code_optional.sql` set every existing account to off (one audit row, `security.sign_in_code_optional`, holds the number of accounts switched).
- A person switches the code **on** for their own account in My Profile (`PUT /auth/profile/sign-in-code` with `{enabled: true}`; it needs an email address on the account). Switching it **off** again needs the current password; a wrong password counts like a wrong sign-in (five tries, then the same timed lock).
- Nobody can change another person's switch. The administrator button that switched a colleague's code off was removed (the route answers 403); a person who lost access to their email uses the password reset link or asks to be unblocked, then switches the code off themselves.
- With the code off, a correct username and password open the session at once. Everything else stays as it was: the lock after wrong tries, the rate limits per address and per account, the audit rows of sign-ins, the forced change of a temporary password, and the reset link (still emailed).
- Advice for every administrator, and for MJ's own Super Admin and Platform Admin accounts: switch the code **on**.

## AI key for the other developer (4 Nov 2026, platform migration 0187)
One key level, `ai`, made by the Super Admin in Platform settings > API access (a reason is required, and a confirmation). It is READ ONLY (GET only; hotels are served in a read-only transaction, so it can change nothing), reaches the console and every hotel (the developer names the hotel in each call with the header `X-HMS-Hotel: <hotel id>`), has no short life (stored as 10 years, shown as "No expiry"; revoke it at any time) and runs 600 calls a minute by default (10 to 3000). Everything a read key may not see for privacy (guests, staff pay, messages, ID photos, mailboxes) is open to it; only the secret-bearing routes stay blocked: sign-in, passwords and one-time links, key management, the settings that hold a secret, online payments, backups, scheduled jobs, invitation links and the paid GST lookup. The call is sent as `Authorization: Bearer hms_pat_...`. It is logged like every key: the last use, the calls of the day, a first use from a new address and every refused call. An address list may be set and is recommended. Anyone with the key reads ALL data: send it over a safe channel and revoke it when the work ends.

## My mailbox: what is isolated, how, and how to add a table (3 Nov 2026; updated for the SES mailbox, platform 0179)
**Isolated:** the address and every list entry, note, quick reply, position, log line and kept email of a staff login's personal mailbox (`platform.pmail_*`, migrations 0178 and 0179). Each person reads and writes only their own rows; another login of any role (a Super Admin cannot read a hotel user's mailbox and the reverse), hotels, groups, guests, companies, visits and API keys read none. There is no mailbox password any more: nothing is connected, and the platform's SES login is never in a personal row.
**Who has one:** the five staff account roles of `common/ui-shared/dashboards/mailboxAccess.ts` (one table, account role only). **Sending:** through the platform's ONE SES sender as the person's own address and nothing else: the fallback chain and the provider failover are for automated system mail; a mailbox never falls back (`mail/personSender.ts`, tested).
**How, in the database (not only in code):**
- every row has `login_id uuid NOT NULL` (foreign key to `platform.logins`, indexed, `ON DELETE CASCADE`), filled by the database from `platform.pmail_login_id()`, which reads the transaction-local setting `hms.pmail_login_id` (`nullif(current_setting(..., true), '')`): an unset or empty setting gives NO rows and no insert;
- `ENABLE` and `FORCE ROW LEVEL SECURITY` on every table (the table owner is fenced too); one policy per table, `USING` and `WITH CHECK` both `login_id = platform.pmail_login_id()`; a trigger `pmail_keep_login_id` refuses any UPDATE that changes `login_id`;
- the setting is set by ONE helper, `withPersonalMailbox(session, work)` (`compose/personalMailbox.ts`; the unit is `repos/postgres/personalMailbox.ts`): inside a transaction, `set_config('hms.pmail_login_id', $1, true)` with a bound value, from the session's own user id; it refuses a session whose id is not its login, an API key, a visit and any account role not in `MAILBOX_ROLES`. The login id never comes from a request. Received mail is delivered the same way, one login at a time, each inside that login's own scope;
- grants to `hms_app` are the least needed (the log is insert-only, the address row is never deleted by the app); `pmail_addresses` holds only the address (unique per login and per address).
**Tests:** `tests/db/personalMailbox.rls.test.ts` runs as `hms_app` with two logins (own rows only, other's id nothing, unset and empty nothing, an INSERT for another login and an UPDATE of `login_id` refused, `relforcerowsecurity` true on every `pmail_` table and a new table without it fails the test, the address table unique per login and per address, the migration guard); `tests/db/personalMailbox.compose.test.ts` runs the real composition on the real database (address, collisions, eligibility, delivery into the right rows); `tests/server/personalMailbox.test.ts` covers eligibility, the address, receiving, SES-only sending and that nobody reads anybody's mailbox.
**To add a table:** name it `pmail_<thing>`; give it `login_id uuid NOT NULL DEFAULT platform.pmail_login_id() REFERENCES platform.logins (id) ON DELETE CASCADE` with an index starting with `login_id`; add the `keep_login_id` trigger; add the table to the `DO $policies$` list in a new migration (ENABLE, FORCE, the `_own_login` policy) and grant only what the code needs; add it to `TABLES` in the DB test; run every query through `withPersonalMailbox`. Update `common/db/hosted-sql-reference.json`.
**Retention:** no job ever deletes a personal list entry or kept email (MJ, 3 Nov 2026). The sidebar unread count is read from the person's own rows only and carries no text, subject or address.
