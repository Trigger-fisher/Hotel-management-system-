# HMS UI: the one document (Next.js, Bootstrap, Pallav theme)

Owner: the UI session (Web UI). This is the **only** UI guide. It replaces `COMPONENTS.md` and `PALLAV-MARKUP.md` (deleted 10 Oct 2026; git history keeps them). If you change anything in the UI layer, change this file in the same commit.
Verified against the code on 10 Oct 2026, sections 1, 2, 5, 7, 8, 9 and 13 to 16 again on 12 Oct 2026 (web-app: Next.js 16.3.8, React 19.2.8, React Compiler on, Tailwind 4, Bootstrap 5.3.3). Rules from MJ and the Lead live in `DECISIONS.md` and win over this file.
The reviewer's separate handbook (pixel scoreboard, premium bar, accessibility) stays in `docs/design/ui-review/`; it is the reviewer's, this file is the builder's.

## 0. The rules in ten lines
1. The look is **Hotel Pallav, 100% the same**, day and night. "Premium" = polish inside Pallav's look, never a new look.
2. The dashboard is **Pallav's own CSS + Bootstrap 5.3.3 CSS**, written in React with **Pallav's own class names and element order**. One Blade view = one TSX file.
3. **No Bootstrap JavaScript.** Modals, dropdowns, tabs, toasts, date and select pickers are React helpers (section 6).
4. **Never edit** a file in `web-app/public/pallav/` except `hms-overrides.css` (each rule there says why) and HMS's own sheets: `conversations.css` (decision 66) and `guest-glass.css` (decision 70, the guest portal's Full Transparent look; every look rule under `body.hms-guest`).
5. **No literal colour or size and no `dark:`** in screens. Use Pallav's variables (`var(--p600)`, `--ink`, `--muted`, `--line`, `--surface`, `--cream` ...), the design tokens (section 14) or Pallav's classes. Night is automatic. `npm run check:shared` proves it (section 15).
6. **Calm motion**: nothing moves on its own. Hover lifts 1px on buttons and 3px on KPI tiles. `hms-overrides.css` switches off Pallav's ambient animation.
7. **Text** comes from `ui-shared` copy files; **money** from `formatINR` (`ui-shared/dashboards/format.ts`) and `wordsOf` for words. No `toLocaleString`, `Intl`, `toFixed` in screens.
8. Every list shows loading (skeleton), empty, error with Try again, and offline.
9. **New UI = use or add a shared component** (section 13). Anything used twice is a helper, not a copy. Screens never define their own button, modal, table, tabs, KPI tile, field, alert, chip or empty state.
10. Check only the file you changed (`npx tsc` on the file or `eslint <file>`); one full review and test at the end (DECISIONS 20).

Facts that bite:
- Night is **not** just darker: the violet scale is inverted, so `var(--p700)` is a *light* violet at night. Always use the variable, never a hex, and never assume `--p*` order means dark to light.
- `pms-dark.css` adds `!important` overrides (`.btn-p`, `.modal-header`, `.kpi-icon`, `.avatar` ...). If a night colour will not change, the cause is there.
- `pms.css` forces `text-align: center !important` on table cells (`:root table > ... td`). Left-align a cell only with a class that out-specifies it, as Pallav's own sheets do.
- The sidebar is a fixed violet gradient in both modes (`#2A0F5E` to `--p800` to `--p700`), not themed.
- Font: Inter (all text), Playfair Display 600/700 only for the brand mark.

## 4. How the dashboard loads its CSS
`PallavFrame` (`pallav/PallavFrame.tsx`) calls `loadPallavBase()` and renders nothing (a blank `#FBF9FF` block) until the base sheets are loaded. Order, as Pallav does it:
1. Base: `bootstrap.min.css`, `bootstrap-icons.css`, `layout.css`, flatpickr, monthSelect, Tom Select CSS, `pms.css`, `pms-ui.css`, `pms-dash.css`, `pms-nav.css`, `pms-payroll.css`, `pms-sidebar.css`, `pms-header.css`, `pms-filterbar.css`.
2. The page's own sheets (`setPageSheets(pageSheetsFor(viewId))`), inserted before night mode. Sheets of the previous screen are removed.
3. Last: `pms-dark.css`, then `hms-overrides.css`.

`pageCss.ts` is the map from view id prefix to sheets (first match wins; copy the list from the Blade view's `@push('styles')`). An id with no rule falls back to `shift-handover.css` only. **When you add a screen, add its rule.** Not every sheet is Pallav's: `conversations.css` (decision 66, HMS's own, Pallav variables only, a `:root[data-theme="dark"]` block, no hex outside variables) is loaded with `shift-handover.css` by `hotel.conversation*` and `platform.conversation*`, and with `settings.css` by `hotel.admin.settings` (its `.cv-settings` block: Settings > Email's Reading and Test connection, Settings > WhatsApp); section 19. `guest-glass.css` (decision 70, HMS's own) is the LAST page sheet of every `guest.*` view, so it follows `portal.css`, `shift-handover.css` and `bill-master.css`; it still loads before `pallav-last.css`, so its look rules are written `:root body.hms-guest ...` (night `:root[data-theme="dark"] body.hms-guest ...`, phones `:root body.hms-guest.portal-mobile ...` inside the 768px query) to out-specify night mode and `hms-overrides.css`, with `!important` only where those use it. Its first block (layout of the guest pages' own `.gg-*` blocks) is unscoped and is also loaded by `hotel.admin.guestPortal`, so the hotel's guest-portal preview gets the structure in the hotel's own look. It is not bundled (no `npm run pallav:css`) and not scanned by check:shared. All links carry `?v=1` (`VERSION` in `assets.ts`): bump it when a vendored sheet changes.

## 5. The shell (do not rebuild)
`RoleDashboard` keeps a **navigation stack** of `{ viewId, params, rootId }`: a menu entry replaces the stack, a drill-in view pushes onto it, `back()` pops. It sets the document title, scrolls to top on a view change, keeps the active menu item visible, and shows `PageSkeleton` while a group chunk loads, "coming soon" when a view id has no screen.
**A reload (`shell/shellSnapshot.ts`, `shell/SnapshotShell.tsx`):** the dashboard keeps a snapshot of what the frame draws (brand, person, menu, header, theme; never a figure or a token) in localStorage, cleared with the shell flag at sign-out. On the next reload the CSS outline carries those words from the first paint (inline script in `app/layout.tsx`), `AppShellSkeleton` draws them after hydration, and the real `PallavShell` renders from the snapshot (`components/auth/DashboardPlaceholder.tsx`) while the session is restored and the dashboard code loads; `RoleDashboard` then replaces it with identical markup. Pallav's stylesheets stay on the page across the hand-over (`PallavFrame` deferred unload). A snapshot shell's menu clicks do nothing until the real shell is there (the view stack is restored with it).

`PallavShell` is Pallav's `layouts/app.blade.php` in React: rail (`#sidebar`), second panel (`#subnav`), optional third panel (`#subnav2`, filled via `panelSlot.ts`), top bar (title tile, greeting + clock, search, accounting-year menu, moon/sun button, Force chip, user menu), the Force banner, then `.content`. It toggles the body classes Pallav's CSS reads: `has-subnav no-subnav sidebar-collapsed subnav-hidden has-subnav2 subnav2-hidden sidebar-peeking subnav-peeking tb-scrolled`. Its optional `look` prop (decision 70; only `'guest'` today, passed by `RoleDashboard` for the guest kind and by `SnapshotShell` for a `guest_user` snapshot) puts `hms-guest` on `<body>` while that shell is shown and removes it on unmount; `app/layout.tsx` writes it into the first server HTML for a guest and `unloadPallav` removes it at sign-out. A body class, not a wrapper, because sheets, the hotel popover, dialogs, toasts and the phone bar are drawn straight under `<body>`. Never use `body.portal-mobile` as a portal scope: every dashboard with a phone bar sets it. Keys: `[` toggles the second panel, `\` the rail, Escape ends a peek. A click on a rail or panel link also ends a hover peek and holds it shut until the pointer leaves (Pallav reloads the page on a click; here the pointer stays on the rail, so the 244px peeked rail stayed over a phone-width page). Phone (Pallav's CSS, kept): under 1081px the rail is icons only (68px), under 761px no side panel is drawn (`wide`); Website pages stay reachable through the section tabs (`WaNav`, scroll sideways), Payroll pages through the Payroll dashboard's own links only (Pallav has no phone menu for them either). Pallav adds `.in` to every `.reveal`; the shell does it with a MutationObserver (and `hms-overrides.css` makes `.reveal` visible anyway).
**What the menu lists** (`shell/navModel.ts` `visibleSections`): an entry shows only when it is not `hidden`, its hotel feature is on, the person may open it, and (for `adminOnly`) the person is an admin. Rules in `ui-shared/dashboards/features.ts`:
- **Grants**: the real session may carry `user.grants` (module key -> level `view | edit | full`; a module the role has no level in is left out). `RoleDashboard` calls `setUserGrants(user.grants)` at sign-in; `moduleOfView(viewId)` maps a menu entry to its module (`hotel.billing.*` bills, `hotel.cash.revenue` revenue, `hotel.cash.expenses` expense, `hotel.cash.handover` handover, `hotel.co.*` companies, `hotel.payroll.*` payroll, `hotel.reports*` reports, `hotel.fo.*` pms, `hotel.web.*` website, `hotel.admin.masters` masters, `hotel.admin.users` users, `hotel.admin.roles` access; anything else is seen by everyone). An entry whose module has no level (or `none`) is not listed. **No `grants` (mock, older sessions) = no filtering**; the server's 403 stays the fallback. A platform or group visitor inside a hotel gets `setUserGrants(null)` (sees the whole hotel, read only); leaving puts the person's own grants back. Test: `web-app/tests/nav.grants.test.ts`.
- **Hotel features**: `NavItem.feature` names one (`pathik` only today); `setHotelFeatures` from session `user.hotel.pathikAvailable` (absent = off; the mock shows them all). The Pathik entry is listed only when the hotel has Pathik (section 12). In Settings, a Hotel Admin who is not the Super Admin sees only the Pathik tab, and only when the hotel has Pathik.

Page **title and icon** come from the menu (`nav.ts` item `pageTitle`, `icon`): never print an `<h1>` in a screen. Screens render inside `.content`; return a fragment, no frame of your own.

A screen's own panel (`usePanel2`, `panelSlot.ts`) becomes the FIRST side panel `#subnav` when the menu has none (Administration: Master Data's lists, as `masters/index.blade.php`), and the second panel `#subnav2` next to a menu panel (Payroll, Website). Top-bar search (mock): `hotelSearchApi(seesUsers)` in `dashboards/search/api.ts` finds screens, guests, reservations, stays, bills and advances (a bill number typed alone ranks first), companies, rooms, room types, user accounts (not for Hotel Users) and payroll staff; hits carry `find` (text for a list) and `open` (an exact record page: stay, reservation, statement, enquiry). Real mode has the server's own kinds only. The shell keeps the last page per user in memory (`shell/lastView.ts`) so unlocking the screen returns to it, and shows a Retry card if a screen crashes or its code fails to load.

**Read-only "Enter hotel"** (Platform console, RESEARCH-PLATFORM-CONSOLE MUST 4): the rule sits in the API layer, not in the screens. `lib/api/mode.ts` keeps `setReadOnlyView(message | null)`; every api made through `chooseApi(real, mock)` is a Proxy that, while the view is on, answers any WRITE method (`isWriteMethod`: the name's first camelCase word is a write verb, `create add update delete remove restore purge set save toggle move reorder bulk refund undo settle reverse cancel checkIn checkOut extend send email generate regenerate make revise unlock lock reset approve reject disable enable import upload run record pay apply confirm decline archive assign clear convert mark void place book block unblock start stop submit ...`; `setActor` and `subscribe` never) with `{ ok: false, error: { code: 'FORBIDDEN', message: 'You are viewing <Hotel> as platform staff. This is read-only.', traceId: 'read-only' } }` without calling the server or the mock, so a blocked save shows the screen's own error and the form stays open. Pass `chooseApi(real, mock, { guard: false })` for an api that is not hotel data (sign-in `lib/auth/api.ts`, preferences `pallav/theme.ts`, search). The shell (`RoleDashboard` `useReadOnlyInside`) turns it on at Enter and off at Exit, at the 60-minute end and on unmount, and only marks write buttons (`.hms-ro-write`, `aria-disabled`, title, click cancelled with the toast): text starting with Save / Delete / Remove / Mark / Restore / Approve / Reset / Unlock / Send ..., a dialog's final New / Add / Create / Record / Refund / Settle / Check in ... button, `.pd-confirm`, icon-only trash / danger buttons. Openers on the page (New bill, Add room, Edit pencil) and wizard Continue / Back / Cancel stay usable, so every form can be opened and looked at. A new screen needs nothing: its api goes through `chooseApi`. Clicking the menu entry of the page already shown starts it afresh (the view key carries a reset counter).

Screen contract (`src/dashboards/types.ts`): a screen is `ComponentType<{ user, params, navigate(viewId, params?), back(), signOut() }>`. A group's `index.ts` exports `screens: Record<viewId, Screen>`. A new view = (1) menu entry in `ui-shared/dashboards/nav.ts` (Lead owns it), (2) screen in its group's map, (3) `pageCss.ts` rule, (4) `groupsFor` prefix if it is a new prefix.

## 6. Writing a screen in Pallav's markup
Source of truth, in order: the running Pallav (`http://127.0.0.1:8000`, login `superadmin`), its Blade view in `%LOCALAPPDATA%\HMS\pallav-ref\resources\views\...` and the CSS file in its `@push('styles')`, demo rows in `docs/sessions/S08-fixtures/` (use as mock rows so both apps show the same numbers).
Translate mechanically: `class` to `className`, `for` to `htmlFor`, `style="a:b"` to `style={{ a: 'b' }}`. **Keep every class and the element order.** No extra wrappers. Blade `@foreach/@if/@php` become TypeScript. Icons: `<Bi name="wallet2" />` (same as `<i className="bi bi-wallet2" />`). Page head: `<div className="page-head"><div><p className="pms-sub">..</p></div><div className="sh-head-actions">..</div></div>` (or `<PageHead sub=..>`). Reference screens: `groups/cash/RevenueScreen.tsx`, `payrollCore/Staff.tsx`, `StaffForm.tsx`, `payrollPay/Payments.tsx`, `companies/ProfilesScreen.tsx`, `CustomerForm.tsx`.

## 7. Bootstrap: what we use and what we do not
- Used: Bootstrap **CSS** (grid `row/col-*`, `form-control`, `form-select`, `btn`, `modal*`, `dropdown*`, `badge`, `table`, `d-flex`, spacing and text utilities) and the **Bootstrap Icons font** (`bi bi-*`).

### Local demo build (mock + quick login in a production build)
`NEXT_PUBLIC_HMS_LOCAL_DEMO=1`, set at **build** time in the command line only (never in a committed file, never in a deploy config, absent from every `.env.example`), keeps the mock API (answers in 40 ms instead of the dev 500 ms), the mock sign-in, the demo accounts panel and the dev quick-login block inside a **local** production build, keeps `/dev/shared-component` reachable, and shows a fixed "LOCAL DEMO" badge on every page (`app/LocalDemoBadge.tsx`). A demo build must have **no database**: the server's env check refuses `DATABASE_URL` together with the flag (`server/config/env.ts`). **Never set it when deploying.** Use: `$env:NEXT_PUBLIC_HMS_LOCAL_DEMO='1'; $env:NEXT_DIST_DIR='.next-demo'; npm run build; npm start -- -p 3010`.

## 8. Next.js 16 rules that apply here
(Read `node_modules/next/dist/docs/` before using any API: this version differs from older ones.)
- One app page for `/` and every dashboard address (`app/page.tsx`, proxy rewrite), plus `/login` (sign-in) and the website at `/` for a signed-out visitor; the dashboard is client state inside that page. Group chunks load with `import()` through the registry; `next/dynamic` is for modals and heavy parts inside a screen.
- `reactCompiler: true`: do not hand-write `useMemo`/`useCallback` unless a measured reason. Do not mutate props or state during render.
- Server Components by default for display-only pieces; `'use client'` only where state or events are used.
- `next.config.ts`: Turbopack root is the repo parent (so `@shared` = `ui-shared/` resolves), `poweredByHeader: false`, `devIndicators: false`, the local-demo flag always inlined (`env`), `/dev/*` answered 404 in a normal production build (`rewrites`), security headers on every path, `Cache-Control: public, max-age=86400, stale-while-revalidate=604800` on `/pallav/*` (Pallav's vendored files keep their names: bump `VERSION` in `assets.ts` when one changes), `pdfkit` external, `distDir` from `NEXT_DIST_DIR`. Search engines: `app/robots.ts` disallows `/` and `layout.tsx` sets `robots: { index: false, follow: false }`.
- Measure speed on `npm run build` then `npm start`, never `npm run dev` (dev compiles each group on first open).

**Measured speed** (numbers and method in `docs/sessions/reports/SPEED-RESULTS.md`, 12 Oct 2026, production builds, headless Chrome probe): on the volume hotel (PERF-Test Hotel: 2,000 bills, 800 customers, 400 staff ...) the median page change over the 26 sidebar pages is **77 ms** (195 ms before `getEveryPage` asked its pages in parallel); Customers 148 ms (was 831), Bills 130, Dashboard 85, Payroll 78. **Not met: Daily Report, 876 to 1213 ms** (the server's `/reports/daily` takes 270 to 540 ms for that data; the rest is the page). Sign-in page: 239 KB JS transferred (budget 250 KB), cold load to the form 366 ms median; code accepted to dashboard ready 995 ms. With the small demo data the page-change median is 38 ms. Server reads: every route's p95 is under the 150 ms budget with 1 user (slowest 49 ms). Not measured yet: LCP, console shell size, search/filter timing on the volume lists, PDFs.
- Respect `prefers-reduced-motion` (already global in `hms-overrides.css`).

## 18. Known risks (UI session, 12 Oct 2026; none of this was run in a browser)

Things to look at first if a page misbehaves while MJ tests. Written from memory of what was changed, not from a test.

1. **Hotel choice re-keys the page** (`shell/RoleDashboard.tsx`: the view key includes the portal hotel). Choosing a hotel remounts the current page, so a half-typed form on a portal page is lost on a switch. Two `HotelSwitch` copies now mount on phones (sidebar and the sticky bar); each loads the hotel list, and both may reset an unknown remembered hotel to "All" (harmless, the same write).
2. **Refresh keeps session and page** (`lib/auth/restore.ts`, `shell/lastView.ts`, `AuthApp`). Restore retries on network or server errors but not on 401. If the server is slow at start, a sign-in screen can flash before the page returns. The remembered page is read from sessionStorage per user and console; a stale entry for a screen the role no longer has is dropped by the stack check, but a renamed view id would fall back to the dashboard.
3. **Mobile CSS** (end of `hms-overrides.css`, `body.portal-mobile`). Never seen on a device. The sticky hotel bar uses a measured `--pt-m-top`; if the top bar changes height after the first paint (font load, a long title wrapping) the bar can sit a few pixels off. `.modal-dialog` is turned into a bottom sheet for every modal while the portal bottom bar is on, including ones that assumed a centred box. The bottom bar covers the last 100 px of a page unless `.content` padding applies (it needs `.main[data-hms-dash]`).
4. **Page-head search position**: most old boxes were left where they were (PageHead, PayLayout, Page head slots); only their look is shared. The Attendance box hides rows with the `hidden` attribute (so typed marks survive); keyboard arrow moves skip hidden rows. The Roles box hides rungs of the ladder; dragging a rung while a filter is on still uses the full list positions.
5. **Guest portal redesign**: built against my own mock until the real routes were tried. The Add member flow sends the picture as base64 in JSON (3 MB becomes about 4 MB of body): a host body limit below that would answer 413, which the screen shows as a generic failure. `signInCodeOn` is not sent by the server yet, so the sign-in code card starts as "off" until it is. The order page's 15-minute check uses the browser clock. (Add member was removed by decision 59.)
6. **Restaurant hours tab** for a non-super Hotel Admin shows even when the hotel has no restaurant; the server checks the Master Data grant, so a user without it sees an error card.
7. **Pathik Submit mode**: the Automatic warning is the only guard in the UI (no second confirmation).
8. **Lint/type rules**: tsc was clean for my files at the last run; `check:shared` and the lint (React Compiler rules) were NOT run on any of this round's files.

## 19. Conversations (decision 66, 24 Oct 2026)
One inbox for a hotel's email and WhatsApp (and the platform's own, in the console). Screens in `groups/conversations/` (`ConversationsScreen`, `ConversationList`, `ThreadView`, `EmailMessage`, `WhatsAppBubble`, `ReplyBox`, `TemplatePicker`, `ContactPanel`, `LinkGuestDialog`, `QuickRepliesModal`, `NotConnected`, `PlatformMailboxSettings`, `PlatformWhatsApp`), view ids `hotel.conversations` / `hotel.conversation` and `platform.conversations` / `platform.conversation`. Contract, copy and sample data: `ui-shared/dashboards/conversations.ts` (+ `.mock.ts`) and `whatsapp.ts` (+ `.mock.ts`); adapter `lib/api/adapters/conversations.ts` (list, summary, thread and body reads are `fresh`; every write is sent with `idempotent: false`); store `groups/conversations/api.ts`. Kit pieces: `ChatBubble`, `MessageTicks`, `ChannelIcon`, `MailFrame` (section 13). Page sheet: `public/pallav/conversations.css` (section 4).
- **Who sees it**: the menu entry is `hotelPrivate`: never listed for Super Admin or Platform Admin inside a hotel (a visit included); a Group Hotel Admin's visit reads only. The server's `access` answer (`canEdit`, `readOnlyReason`, `canSeeStay`, `canSeeBills`, `canLink`) decides every control; a read-only person sees the reply box, notes, Assign and Link guest disabled with the reason ("Read only during a visit." or the view-only sentence), never hidden.
- **Layout**: from 1200 px list | thread | contact panel; 761 to 1199 px list | thread with the contact panel as a right-side drawer (the "i" button); under 761 px one pane: the list, or the thread full screen with a back button to the scope's list (tab, channel and scroll kept in module memory), the contact panel as a bottom sheet, the bottom bar hidden, `100dvh`, the reply box sticky above the keyboard with the safe-area inset, 16 px inputs, 44 px targets. Phone head: full-width search, the tabs as a sideways row, the channel filter in `FilterMenu`, "Check now" as an icon button.
- **Keyboard and screen readers**: (1) the list is a `role="listbox"` with one roving tab stop: Up and Down move, Home and End jump, Enter opens; the open row has `aria-selected` and `aria-current` (`listKeys.ts`, a pure reducer with its test); (2) Ctrl+Enter (Cmd+Enter on a Mac) sends, Enter is a new line, on both channels ("Ctrl+Enter to send" under Send); (3) opening a thread moves focus to its heading; Esc on a phone thread returns to the list with focus on that row; Esc closes the contact drawer, the sheet and the modals, focus back on the opener; (4) a visually hidden `aria-live="polite"` region announces new inbound messages found by polling as "{n} new message(s) from {name}" (the name only, never the text); (5) `/` focuses the list search unless you are typing in a field; (6) ticks and channel icons carry their words.
- **Email**: the newest email of a thread opens by itself (one body request per thread open), the others on click; a skeleton while it loads, an inline Alert with Try again when it fails, "Too large to open here" with the size; bodies live in component state only. Remote pictures are hidden until "Show images"; an unverified sender gets a warning Alert; a different Reply-To is offered on purpose, never used by default; "Attach bill" appears only when the person may see bills, the thread is linked and the reply goes to the contact's own address.
- **Polling**: the page checks the mailbox on opening and every 60 s, then reads the list again; an open thread is read every 15 s and new messages are merged by id. Elsewhere the menu badge (`shell/conversationsUnread.ts`) sends one `syncMail({ background: true })` every 90 s while the tab is visible (its answer carries the unread count), waits while the page itself polls and stops for the session after "needs the latest database update" or a 403. No message text, subject or address is ever kept in browser storage.
- **First run**: with nothing read yet, the mailbox off or not available and WhatsApp not connected, the panes give way to the setup cards (`NotConnected`): what reading does, the privacy warning, and the next step for the person's role. On the live site WhatsApp shows "WhatsApp not connected yet" with a disabled Connect ("Coming soon").
