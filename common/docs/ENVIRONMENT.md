# Environment reference

Every setting the running app and the database scripts read. Names only here: values live in `web-app/.env.local` (app) and `db/.env.local` (scripts), both git-ignored, or in the host's secret store. The app checks its environment once, at start (`web-app/src/server/config/env.ts`); in production a missing or unsafe setting stops the server with the NAME of what is wrong (never a value). Run `node scripts/smoke.mjs <address>` after every deploy.

## 1. The running app (`web-app`)

| Name | Production | Default | Meaning |
|---|---|---|---|
| `NODE_ENV` | `production` | `development` | `production` turns on the fail-closed checks, HSTS and the content policy. `next start` sets it. |
| `DATABASE_URL` | **required** | none | `postgresql://hms_app:...@host:port/hms` : the limited app role. Never the owner or a superuser. |
| `HMS_HASH_KEY` | **required** | none | Base64 of at least 32 random bytes. Keys the hashes of one-time codes and sign-in names. **Never regenerate**: every pending code and invitation stops working. Back it up with the database. |
| `HMS_SECRET_KEY` | **required** | none | Base64 of exactly 32 random bytes (`setup` writes one). The app's encryption key (AES-256-GCM, the hotel id bound in). Separate from `HMS_HASH_KEY`. **Never lose it**: values sealed with it cannot be opened without it. Back it up apart from the database dumps. |
| `HMS_DATA_KEY` | optional now, **required** once ID and bank numbers are sealed (decision 74) | none | Base64 of exactly 32 random bytes (`setup` writes one). Seals ID numbers, bank account numbers and IFSC codes (AES-256-GCM, bound to the hotel and the field) and builds their search index. Separate from `HMS_SECRET_KEY` and `HMS_HASH_KEY`. **Never lose it**: without it the sealed numbers cannot be opened. Back it up apart from the database dumps. |
| `HMS_PUBLIC_URL` | **required**, `https://`, not localhost | `http://localhost:3000` | The address people open; invitation links in e-mails are built from it. No path. |
| `MAIL_DRIVER` | **must be `smtp`** | `log` | `log` prints one-time codes to a terminal: development only, refused in production. |
| `SMTP_HOST`, `SMTP_FROM` | required with `smtp` | none | Mail server and sender (`noreply@hotel.in` or `Hotel <noreply@hotel.in>`). Platform settings (Mail sender) win over `SMTP_FROM`. The mail server the Super Admin saves in Platform settings > Mail (host, port, security, login, password) is used FIRST; these variables are the fallback while that is empty. |
| `SMTP_SECRET_KEY` | optional (the app starts without it) | none | Base64 of exactly 32 random bytes (`node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`). **Not needed for Gmail: leave it out.** The key that seals the Gmail app password (Platform settings > Mail and each hotel's Settings > Email; AES-256-GCM, fresh IV per value, stored as `v1.iv.tag.data`) is DERIVED from `HMS_HASH_KEY` with HKDF (SHA-256, fixed info `hms-smtp-v1`, 32 bytes), so saving a password works as soon as `HMS_HASH_KEY` is set. If `SMTP_SECRET_KEY` is set it WINS (an override): passwords sealed with a different key cannot be opened. If a saved password cannot be opened (the key changed), mail falls back to the server's `SMTP_*` settings (platform) or the platform sender (hotel) and the screen shows a notice: save the app password again. Do not change `HMS_HASH_KEY` after saving passwords without re-saving them. From 18 Oct 2026 every mail service (Amazon SES, Brevo, Gmail, other SMTP) is set from the screens only, and its password is write-only; no `SMTP_*` variable is required (they stay as the optional fallback while nothing is saved). Conversations (decision 66): the SAME sealed password also opens the mailbox for reading (IMAP), so a key change that makes it unreadable stops reading as well as sending until it is saved again (the Conversations page says "The saved app password cannot be opened on this server. Type it again in Settings > Email and save."); no new variable. |
| `SMTP_PORT` | | `587` | 587 = STARTTLS (required), 465 = TLS from the first byte. |
| `SMTP_SECURE` | | true only for 465 | `true` or `false`. Mail needs STARTTLS on a non-secure port: `SMTP_SECURE` unset or `false` with port 587 uses STARTTLS (Gmail on 587 is fine); `SMTP_SECURE=true` is for port 465 only. |
| `SMTP_USER`, `SMTP_PASS` | together or neither | none | Mail login. |
| `DB_POOL_MAX` | | `20` (outside production: `5`; on Vercel: `3`) | Size of the one shared connection pool (all hotels share it). On a serverless host behind a pooler 1 to 3 per function instance. See section 4. |
| `DB_POOL_MIN` | | `4` (outside production and on Vercel: `0`) | Connections kept open between bursts. Keep it `0` on Vercel: the pool sets no idle timer on a connection at or below this number, so a kept one is never closed and can come back as a dead socket after the function instance was suspended for minutes (the first request would then hang). |
| `DB_POOL_IDLE_SECONDS` | | `600` (outside production: `30`; on Vercel: `300`) | Seconds an idle connection above `DB_POOL_MIN` is kept before it is closed. On Vercel 300 s keeps a connection to the pooler open across the short gaps between a person's requests, so they do not pay the 1 to 1.3 s of a new connection each time; one idle through a suspension is closed on thaw and the next request opens a fresh one. The Vercel defaults apply only when these three variables are UNSET: a project that still sets `DB_POOL_IDLE_SECONDS=10` (the value the first deploy guides gave) should set it to `300`, or remove the variable so the default applies. |
| `DB_POOLED` | `1` behind a pooler | unset | `1` = the address goes through a transaction pooler (Supabase transaction pooler, PgBouncer): no startup options are sent (the `hms_app` role carries timezone=UTC itself). |
| `MEDIA_DRIVER` | leave unset on Vercel | unset: `db` on Vercel with a database, else `local` | Where photos are kept: `db` = the platform database (table `platform.media_files`, platform migration 0137; no bucket; ID photos are stored as a JPEG of about 400 KB; the nightly backup copies then have no store here), `local` = this server's disk (`HMS_MEDIA_DIR`; on Vercel it means uploads are refused), `s3` = a private S3-compatible bucket (website media under `media/`, guest ID photos under `id-photos/`, the nightly backup copies under `backups/`; with `local` the copies go to a `backups` folder beside the media folder). With `s3` in production the five `S3_*` settings are required. |
| `S3_ENDPOINT` | required with `s3`, `https://` | none | The bucket provider's endpoint, no path (`https://s3.ap-south-1.amazonaws.com`, `https://<account>.r2.cloudflarestorage.com`); the one exception is Supabase Storage, `https://<project>.storage.supabase.co/storage/v1/s3` (with `S3_FORCE_PATH_STYLE=1`). Plain http only to this machine. The same bucket also holds the files of an email under `temp-email/<hotel id>/` (added in Compose, sent as attachments, removed one hour after a successful send by `/api/v1/cron/mail-files`; `mail/files.ts`). |
| `S3_REGION` | required with `s3` | none | The bucket's region (`ap-south-1`; `auto` for R2). |
| `S3_BUCKET` | required with `s3` | none | The bucket name. The bucket must be private: HMS serves every file itself after a permission check. |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | required with `s3` | none | An access key limited to that bucket's objects (read, write, delete). Read by the running app only; never logged, returned or put in an error. |
| `S3_FORCE_PATH_STYLE` | | unset | `1` = `endpoint/bucket/key` addresses (MinIO and most self-hosted stores); unset = `bucket.endpoint/key`. |
| `HMS_MAIL_WORKER` | `cron` on Vercel | `in-process` | How the mail queue is sent: `in-process` = a timer in the server (VPS, local), woken within a quarter of a second of a mail being queued; `cron` = no timer: the request that queues a mail runs one pass right after it has answered (so a code or an enquiry mail leaves within seconds), and a scheduler calling `GET /api/v1/cron/mail` with `CRON_SECRET` every few minutes is the safety net for retries (serverless hosts). Each pass sends up to 50 mails, 8 at a time, and a mail that names a hotel goes through that hotel's own mail server (Settings > Email; `docs/BACKEND.md`). |
| `HMS_ALERT_WEBHOOK` | recommended | none | An `https://` incoming webhook (Slack, Discord, Teams, Axiom, any monitor that takes a JSON POST). Every error-level log line is also POSTed there as `{text, level, time, msg, traceId}` (already redacted), at most 20 a minute; nothing else is sent, and a webhook that fails never affects the app. Unset: errors are only logged. |
| `HMS_SECURITY_SLACK_WEBHOOK` | optional | none | Security alerts (plan `security/docs/SECURITY-INTEGRATION-PLAN-2026-11-01.md` section 7): a Slack incoming webhook, `https://hooks.slack.com/services/...` only. Warning and Critical events are posted there; unset = dormant. |
| `HMS_SECURITY_SMS_PROVIDER` | optional | none | `msg91` or `twilio`: sends an SMS for Critical events only. Needs `HMS_SECURITY_SMS_TO` (E.164 numbers, comma separated) and that provider's keys: MSG91 `MSG91_AUTH_KEY` + `MSG91_TEMPLATE_ID` (a flow template with one variable, `var1`); Twilio `TWILIO_ACCOUNT_SID` + `TWILIO_AUTH_TOKEN` + `TWILIO_FROM`. The app refuses to start if the provider is set without them. At most one SMS per kind and address every 10 minutes. |
| `TURNSTILE_SECRET_KEY`, `NEXT_PUBLIC_TURNSTILE_SITE_KEY` | optional | none | Cloudflare Turnstile security check on sign-in, forgot password and the emailed reset link (set both or neither). The secret key is read by the server only (`server/http/turnstile.ts`); the site key is public. With a secret set, a request without a good token is refused (422, `fields.captcha`) and so is one made while Cloudflare cannot be reached. Add the live domain (and localhost for development) to the widget's hostnames. Unset: no check. |
| `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ZONE_ID` | optional | none | Connect the layer 1 emergency reset to the Cloudflare zone (set both or neither). Token scope: this zone only, Zone Settings read and Firewall Services edit. Unset: the edge reset says "not connected" and ends unhealthy. |
| `CRON_SECRET` | required with `cron` | none | At least 32 random characters: the bearer secret of `/api/v1/cron/*` (`Authorization: Bearer <CRON_SECRET>`; Vercel Cron sends it when the variable is set on the project). Unset: those routes answer 404. Routes: `/cron/mail` (the queue), `/cron/daily-summary` (the owners' evening summary, once a day), `/cron/conversations` (Conversations, decision 66: first the 12-month purge of every hotel's and the platform's email list, then the safety-net mail check of the mailboxes with reading on, a few at a time; when time runs short it calls itself again with `?detached=1`). `web-app/vercel.json` schedules them once a day (Hobby allows daily crons): mail 02:00 UTC, daily summary 15:30 UTC, conversations 01:00 UTC. |
| `HMS_PATHIK_RUNNER` | `online` to run Pathik on Vercel | `pc` | Who runs the Pathik cycle: `pc` = the worker on a PC or VPS polls HMS (`pathik/worker`); `online` = this app runs it in a serverless function (`/api/v1/cron/pathik`, the one route that carries `@sparticuz/chromium`): a check-in, a check-out, the Run now button and an open Pathik page kick a run for that hotel through the app's own address (`HMS_PUBLIC_URL`, else the host's own name) with `CRON_SECRET`; the daily Vercel cron is the safety net. Hotels must be set to Automatic submit. Guide: `docs/pathik/PATHIK-ONLINE.md`. |
| `PATHIK_CHROMIUM_PATH` | never on Vercel | none | Online runner on a PC with Chrome installed (a local test): run this browser instead of the serverless Chromium. |
| `PATHIK_PORTAL_URL`, `PATHIK_ALLOW_REAL` | `yes` to allow the real site | `https://pathik.guru`, unset | Online runner: the Pathik address and the go gate for the real portal (without `yes` only a local address is allowed). |
| `LOG_LEVEL` | | `info` | `debug`, `info`, `warn`, `error`, `silent`. Logs are one JSON line each with a `traceId`; passwords, codes, tokens and ID numbers are redacted. |
| `HMS_MEDIA_DIR` | | `web-app/.data/media` | Absolute folder for uploaded website photos. Must be on persistent disk and backed up with the database. |

Refused in production (the app will not start): `HMS_DEV_RELAX_LIMITS` (development throttle relaxation), `NEXT_PUBLIC_API=mock`, any of `PGSUPERUSER_URL`, `PG_OWNER_URL`, `PG_TEST_OWNER_URL`, `PG_CONSOLE_URL`, `PG_APP_DIRECT_URL` in the app's environment, `MEDIA_DRIVER=s3` without all five `S3_*` settings or with a non-https `S3_ENDPOINT`, `HMS_MAIL_WORKER=cron` without `CRON_SECRET`, `HMS_MAIL_WORKER` other than `cron` on Vercel (`VERCEL` set by the host: a serverless function has no timer, so no sign-in code would ever be sent), and `NEXT_PUBLIC_HMS_LOCAL_DEMO=1` together with a database (the local demo build has mock data and no database; see `docs/UI.md`).

Warned at boot (the app starts, but writes one `warn` log line at start and shows the same sentence under System Health `notices`): `MEDIA_DRIVER` unset or `local` on Vercel with a database ("Photo storage is not set up on this server yet": every photo upload, website gallery, icons, logo and guest ID photos, answers a plain 503 with that sentence instead of a 500; reading a photo answers 404; set `MEDIA_DRIVER=s3` and the five `S3_*` settings), and a database login other than `hms_app` (asked once with `SELECT current_user`; only the login's name is logged, never the connection string: put the `hms_app` login in `DATABASE_URL`).

Build time: `next build` does not need the production secrets (the checks run when the server starts, `NEXT_PHASE=phase-production-build` skips them). `NEXT_PUBLIC_*` values are baked into the build.

## 2. The database scripts (`db/`, run from `web-app` with `npm run db:cli -- ...`)

| Name | Where | Meaning |
|---|---|---|
| `PGSUPERUSER_URL` | `db/.env.local` | A server-level login that can create roles and databases. Used by `setup` and `restore-check` only. Delete it from the machine once the server is set up if you can. |
| `PG_OWNER_URL` | `db/.env.local` | `hms_owner` on database `hms`: runs migrations, seeds, hotel creation, backups. Owns everything. Never given to the app. |
| `PG_TEST_OWNER_URL` | `db/.env.local` | `hms_owner` on `hms_test` (development machines only; tests). Not needed on a server. |
| `PG_BIN` | environment | Folder of `pg_dump`/`pg_restore` when they are not on the `PATH` (on Windows the default is `C:\Program Files\PostgreSQL\18\bin`). |

The two secret files are separate on purpose: the app can be started without the scripts' secrets and the scripts without the app's.

## 3. Files on disk that matter

| Path | What | Back up |
|---|---|---|
| the database `hms` | everything | yes (section "Backup" in `docs/OPERATIONS.md`) |
| `HMS_MEDIA_DIR` | website photos | yes, with the database |
| `db/dumps/backups/` | backups made by `db:cli backup` | copy off the machine |
| `db/dumps/exports/` | hotel exports made before a permanent delete | keep as long as the hotel's data must be recoverable |
| `db/.dev-*` | development logins and mail log | never on a server; git-ignored |

## 4. Connection pool sizing

One pool per app process serves all hotels. A request takes one connection for its transaction (`BEGIN`, one `set_config` statement for the hotel's role and search path, work, `COMMIT`) and gives it back; the app role limits each statement to 15 s, an idle transaction to 10 s and a lock wait to 5 s. Rule of thumb: `DB_POOL_MAX` = 20 for one instance serving a few dozen busy staff; PostgreSQL `max_connections` must be at least `DB_POOL_MAX x number of app instances + 10` (scripts, backups, an admin session). On a small managed database with a low connection cap, lower `DB_POOL_MAX` (for example 5 to 10) rather than raising the cap.

Production runs through the Supabase transaction pooler (port 6543) with `DB_POOLED=1` (PgBouncer in transaction mode): a connection is the app's only for one transaction, so no session state survives a transaction (that is why `withHotel` sets the role and the search path with `set_config(..., true)` inside `BEGIN ... COMMIT`) and named prepared statements are not used. On Vercel a warm function instance keeps a connection to the pooler open for 300 idle seconds and none for ever (`DB_POOL_MIN=0`, `DB_POOL_IDLE_SECONDS=300` by default: a connection at or below `DB_POOL_MIN` gets no idle timer, so with `1` a dead socket could survive a suspension of the instance); every connection counts against the database's connection cap, so 3 per instance is the most. The deploy guides (`docs/deploy/DEPLOY-HOSTED.md`, `docs/deploy/SUPABASE-MOVE-2026-10-18.md`) give the same values; a project that still has `DB_POOL_IDLE_SECONDS=10` from an earlier deploy should change it to `300`.
